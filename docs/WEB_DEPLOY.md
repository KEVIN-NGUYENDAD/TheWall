# THE WALL — Web Deploy Guide

The production Web build lives in `web_release/` at the project root (`index.html`,
`index.js`, `index.wasm`, `index.pck`, plus the audio worklet and icon files
Godot generates alongside it). This build was produced with:
`godot --headless --export-release "Web" web_release/index.html`, using the
`Web` preset in `export_presets.cfg` (`html/canvas_resize_policy=2`, i.e.
Adaptive — the canvas fills and resizes with the browser viewport, which is
what gives correct scaling on both phone and tablet aspect ratios).

## What's in `web_release/`

```
web_release/
├── index.html                       entry point
├── index.js                         Godot's Web runtime glue
├── index.wasm                       the actual game engine + your code (~38MB)
├── index.pck                        packed game data (scenes, scripts, resources)
├── index.audio.worklet.js           audio thread worklet
├── index.audio.position.worklet.js  audio position tracking worklet
├── index.png / index.icon.png / index.apple-touch-icon.png   favicons
```

All of these must be deployed together, in the same directory, served over
**HTTPS** (required for the WebAssembly + SharedArrayBuffer features Godot's
Web export uses — `file://` and plain HTTP will not work correctly).

## Deploy to GitHub Pages

1. Commit `web_release/` to your repo (or a dedicated `gh-pages` branch /
   `docs/` folder, depending on your preferred Pages source).
2. In the repo: **Settings → Pages → Build and deployment → Source**, pick
   the branch and folder containing `web_release/`'s contents at its root
   (GitHub Pages serves from the folder root, so either put these files
   directly in the Pages source folder, or point Pages at `web_release/` if
   your chosen source supports a subfolder).
3. Wait for the Pages build to finish, then open the published URL.
4. **Cross-origin isolation note**: Godot's Web export needs
   `Cross-Origin-Opener-Policy: same-origin` and
   `Cross-Origin-Embedder-Policy: require-corp` response headers for
   multithreading/SharedArrayBuffer to work. GitHub Pages does **not** let
   you set custom response headers. If the build fails to start or hangs on
   load in the browser console with a SharedArrayBuffer/threading error,
   this is why — GitHub Pages works for single-threaded exports (check
   `variant/thread_support` in the preset; this project's preset has it set
   to `false`, which is the compatible choice for GitHub Pages) but will not
   work if threading is ever turned on later without switching hosts.

## Deploy to Netlify

1. Drag-and-drop the `web_release/` folder onto Netlify's deploy UI, or
   connect the repo and set the **Publish directory** to `web_release`.
2. Netlify serves over HTTPS by default — no extra TLS setup needed.
3. To set the cross-origin headers properly (recommended, and required if
   thread support is ever enabled), add a `_headers` file inside
   `web_release/` before deploying:
   ```
   /*
     Cross-Origin-Opener-Policy: same-origin
     Cross-Origin-Embedder-Policy: require-corp
   ```
   Netlify reads this automatically; no dashboard configuration required.
4. Redeploy any time `web_release/` is regenerated by re-running the export
   command above and re-uploading / re-pushing.

## iPad testing instructions

1. Open Safari on the iPad and navigate to the deployed URL (Chrome/Firefox
   on iOS use Safari's WebKit engine underneath, so Safari is the most
   representative test).
2. **Add to Home Screen** (Share button → Add to Home Screen) for a
   full-screen, browser-chrome-free test closer to how a real player would
   experience it.
3. Confirm on load:
   - The canvas fills the screen without letterboxing or stretching
     artifacts (Adaptive resize policy should handle this automatically)
   - Touch controls (Left/Right/Jump, Pause) appear at a size that's
     comfortable for a tablet-sized thumb reach, not just phone-sized
   - Rendering is sharp, not blurred — if it reads as blurry on a Retina
     iPad, this is a known open item (see `KNOWN_BUGS.md` / prior
     `EXPORT_ANDROID.md` notes on device-pixel-ratio scaling); it is not
     something this Web export pass can fully resolve without a custom HTML
     shell that accounts for `devicePixelRatio`, which is out of scope here
4. Play through: charge-jump, movement, dash (double-tap), a checkpoint, a
   death (confirm the death screen and death marker appear), and a memory
   reveal if you can reach 100m.
5. Background the Safari tab and return — confirm the game resumes without
   a hard crash (Web audio contexts sometimes need a tap to resume; this is
   normal browser behavior, not a bug in the game).

## iPhone testing instructions

1. Same URL, Safari on iPhone, Add to Home Screen as above.
2. Pay specific attention to touch target size — iPhone screens are smaller
   than iPad, so the same button sizes that felt fine on a tablet may feel
   cramped on a phone. Note this explicitly rather than assuming iPad
   testing covers it.
3. Confirm portrait lock holds (the project forces portrait via
   `window/handheld/orientation`, but this is a project *setting*, not an
   OS-level lock — a physically rotated phone should not visually rotate the
   canvas; if it does, that's worth reporting as a bug, since Web exports
   don't get the same native orientation-lock guarantee as an installed
   Android/iOS app).
4. Test with Low Power Mode on and off — WebAssembly + WebGL performance can
   dip noticeably under iOS power throttling; note any frame-rate issues
   specifically under Low Power Mode.
5. Same functional pass as iPad: charge-jump, dash, checkpoint, death,
   memory reveal.

## Known limitation

This guide was written after actually running the export
(`godot --headless --export-release "Web" web_release/index.html`) and
confirming all expected files were produced — but the resulting build has
**not** been opened in an actual browser or on actual iPad/iPhone hardware
from this environment, since neither is available here. Treat the first real
browser load as the first real test of this specific build.
